# Before and after publishing

Two things go wrong when work from this repository reaches GitHub: an assistant
credit line gets attached, and prose written for a machine reader gets published to
a human one. Both are cheap to catch and awkward to undo, so run both passes.

Run them as two independent sweeps. They look at the same artifacts for different
reasons, and folding them together means one gets skimmed.

## Pass 1 - attribution

Nothing published from this repository credits an AI assistant. `CLAUDE.md` and
`tooling-invariants` state the rule; this is how to check it holds.

**What counts as attribution:** a `Co-Authored-By` trailer naming an assistant, a
"Generated by" or "Generated with" footer, a link to an assistant session, a signed
comment. **What does not:** naming a model in prose, and the `.claude/skills/` path,
which the tooling fixes and which appears legitimately in any description of this
repo's layout. Do not "clean up" either - that is over-correction, and it breaks the
vendored `sepia` copy that `UPSTREAM.md` keeps byte-identical to upstream.

**The order that matters:** the footer is appended when a pull request is *created*,
not when it is edited. So create, then immediately re-read the body and strip it, then
verify by reading again. Assuming the edit worked is how one shipped.

Sweep, in this order:

1. **Files** - `Test-Modpack.ps1` covers these with its `no agent attribution
   committed` check. It scans tracked `.md`, `.ps1`, `.json`, `.yml` and `.sh`
   content for the credit markers. It reads and throws; it never edits.
2. **Pull request bodies** - fetch each one and read what is actually stored, not
   what you submitted. These differ.
3. **Comments and reviews** - on every pull request the work touches, not only the
   current one.
4. **Commit messages** - `git log --format="%s%n%b"` for trailers, and
   `git log --format="%an <%ae>"` to confirm the author is the repository owner.

Steps 2 to 4 are outside any repo-side check's reach. That is the gap the file check
cannot close, and the reason this pass is manual.

## Pass 2 - prose

Anything the change adds in prose - a pull request body, a README section, a skill,
release notes - goes through the `sepia` skill's **review** operation before it is
published. Route on the artifact: `references/domains/dev-replies.md` for comments and
review replies, `references/domains/release-notes.md` for release text, and
`references/domains/tech-articles.md` with `professional-pass.md` for documentation.

**Use this repository's README as the venue corpus.** It is the largest piece of prose
here that no assistant wrote, which makes it the honest target register rather than a
generic idea of good writing. Measuring against it has already caught real drift: the
skills once ran about 60% above its em-dash density.

Review diagnoses; it does not edit. Apply findings only after reading them, and skew
towards deleting and replacing rather than adding.

## Reporting what the passes found

Say which artifacts were checked and what was found, including "nothing". An audit
that only speaks up when it finds something is indistinguishable from an audit that
did not run.

Where a pass cannot reach - commit messages already pushed, a comment on a merged
pull request - say so rather than implying coverage. The value of these sweeps is
knowing exactly what they do and do not see.
